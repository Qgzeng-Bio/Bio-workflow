## 验证过程与范围

1. 首轮维护用小型反例修复三处论文溯源边界问题。
2. 独立复核提出的集合、Git读取/tag身份、路径归属、逐图源表及acceptance下游重读问题，经过红→绿回归和只读复核关闭。
3. 该维护版本的源码全套检查在本地隔离临时目录完成，约67秒。此前一次180秒超时也保留在本地记录，不被记为PASS。
4. 后续按用户要求顺序执行两轮审查：
   - 第一轮修复同步目标末尾路径拼写的软链接漏检、元数据父目录软链接读取和超深Markdown anchor漏检；按用户选择对齐v1角色范围。
   - 第二轮修复Shell语法检查只覆盖首文件的问题，去掉重复active-card验证，并仅在单次paper审计内复用索引/源表解析。
5. 两轮后的当前版本进行了受影响部分的定向验证，不宣称又重跑了一次完整基线。

通过的定向检查：

```bash
python3 -B scripts/test_sync_install.py
python3 -B scripts/test_maintenance_modes.py
python3 -B scripts/test_publication_trace_audit.py
python3 -B scripts/test_reference_consistency.py
python3 -B scripts/validate_program_cards.py --check-drafts
for file in scripts/*.sh assets/slurm-templates/*.sbatch; do
    bash -n "$file" || exit
done
git diff --check
```

两个Claim共享输入的小型fixture中，版本索引解析2→1次、图索引4→1次、两个源表验证4→2次。共享坏输入仍分别产生Draft WARN和Reviewed BLOCK，缓存命中不绕过当前图归属，下次审计重新检查。该计数不是实际大项目耗时benchmark。

测试只使用隔离临时项目、fake工具链/SLURM及临时Git仓库；不会提交真实作业。测试自身可创建临时文件和fixture提交/tag，不能将它描述成全过程零写入。
